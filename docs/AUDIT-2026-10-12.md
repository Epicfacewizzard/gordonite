## Findings

1. **P2 — task lists remain stale after other-device edits.** `client/src/views/Tasks.jsx:89–100` loads only on mount (and after a failed task action); it does not refresh on focus or subscribe to note changes. An isolated browser probe opened Tasks, saved a new task through the API as another device, and dispatched a focus event. The task remained absent until reload. Refresh on focus/reconnect and reconcile local pending edits when rebuilding the list. The dashboard uses the same component.
2. **P2 — repeated Load more taps duplicate note rows.** `client/src/views/Notes.jsx:59–68,142` leaves the button enabled while a request runs. Two requests use the same offset and append the same results. An isolated browser probe seeded 35 notes, held two offset-30 requests, then released both: 40 rows appeared for 35 unique note links. Guard against concurrent requests, disable the button while loading, and deduplicate by note ID.
3. **P2 — the global conflict indicator cannot navigate to an untagged note.** `client/src/app.jsx:48–50` navigates only if the conflicted session has a first tag. For an untagged free note the click does nothing, so users must find its note page manually to resolve it. Source-confirmed; not reproduced in a two-device browser scenario. Navigate directly to the conflicted note's ID.
4. **P3 — task-edit regression test targets an obsolete dashboard view.** `tests/e2e/task-text-edit.test.js:16–18` seeds an undated task and expects it on the default dashboard, which now shows overdue/due-today tasks. The existing test times out before exercising editing. In the isolated copy, changing only the destination to `#/tasks` makes its formatting, nested-task preservation, undo/redo and offline recovery checks pass. This explains this particular documented failure; other documented failures were not investigated.
